# RepoTutor 项目面试八股文

本文用于面试前快速复盘 RepoTutor。建议先背熟“项目总述”和“核心亮点”，再按面试官追问方向展开细节。

适用版本：当前 `main` 分支，覆盖 V1 主学习闭环、V1.1/V1.2/V1.3 面试包装增强，以及 V2 变更理解、PR 讲解、增量学习和源码追问能力。

## 1. 一句话介绍

RepoTutor 是一个面向 Python/FastAPI 项目的交互式 AI 代码导师。用户上传项目 ZIP 或导入公开 GitHub 仓库后，系统会安全解压并通过 AST 静态分析建立项目事实库，自动生成架构图、学习路线、课程、测验、掌握度反馈、低分补课材料、面试准备材料和变更理解报告，帮助用户系统理解和接手一个陌生代码库。

更口语化地讲：

> 这个项目不是简单问 AI“这段代码是什么意思”，而是把一个陌生 FastAPI 仓库整理成一套可学习、可测验、可追踪的课程体系。

如果面试官更关注业务价值，可以说：

> RepoTutor 的定位是“项目接手加速器”：既能帮新人看懂代码，也能把一次 diff 变成影响范围、PR 讲解、复习课程和源码追问清单。

## 2. 项目背景怎么讲

很多人学习陌生后端项目时会遇到几个问题：

- 不知道先看哪个文件。
- 看得懂单个函数，但串不起来入口、路由、业务层、数据层。
- 对项目架构图、调用链、核心模块没有整体认识。
- 学完以后容易忘，也不知道自己哪里没掌握。
- 普通 AI 问答只能回答单个问题，不能持续管理学习过程。
- 做代码变更时，很多人只看修改文件，容易漏掉受影响的调用方、路由和测试。

RepoTutor 解决的是：

> 如何把一个真实代码仓库变成一套可学习、可测验、可反馈的课程。

到 V2 阶段，问题进一步扩展为：

> 如何把一次代码变更变成可解释的影响分析、PR 讲解材料、增量学习计划和源码追问入口。

## 3. 适合放在简历上的描述

可以写成：

> 设计并实现 RepoTutor，一个面向 Python/FastAPI 代码库的交互式 AI 代码导师。系统通过 ZIP 安全解压、GitHub URL 导入、AST 静态分析、文件依赖图和函数级调用链构建项目事实库，自动生成专业架构图、个性化学习路线、课程讲解、测验评估、低分补课、面试准备、PR 讲解包和增量学习建议，并通过 FastAPI、Streamlit、SQLite、LangGraph 和 OpenAI 兼容接口完成端到端闭环。

如果简历空间有限，可以压缩成：

> 基于 FastAPI + Streamlit + SQLite + LangGraph 实现 AI 代码导师，支持上传或导入 FastAPI 项目后自动完成静态分析、架构图生成、学习路线规划、课程测验、掌握度追踪、动态补课、面试包装和 diff 变更理解。

## 4. 技术栈

后端：

- FastAPI：提供项目上传、GitHub 导入、分析、课程、测验、报告、问答、变更理解等 API。
- SQLite：保存项目、学习画像、分析结果、课程、测验、掌握度、Agent 运行记录和 LLM 审计。
- Python AST：静态分析源码，提取类、函数、路由、模型、Schema 和调用关系。
- LangGraph：编排项目导入工作流。
- OpenAI 兼容接口：可选增强课程和项目问答，输出失败时回退确定性结果。

前端：

- Streamlit：快速构建交互式学习界面。
- 多页面结构：项目导入、项目概览、架构图、学习路线、课程测验、源码浏览、复习中心、面试准备、Diff 影响分析、PR 讲解包、增量学习、源码追问等。

工程：

- Docker Compose：一键启动后端和前端。
- pytest：覆盖核心分析、Agent、课程、测验、补课、报告和工作流。
- GitHub Actions：持续集成。
- Markdown 报告导出：项目学习报告、单节课程报告、演示讲稿、面试材料、PR 讲解包和增量学习建议。

## 5. 项目整体架构

可以按四层讲：

```text
Streamlit Frontend
  -> FastAPI API
  -> Service / Agent / Analyzer
  -> SQLite + Artifact Files
```

再展开：

- 前端负责上传项目、选择学习画像、展示分析结果、课程、测验、架构图和报告。
- FastAPI 负责统一暴露接口，包括上传、分析、课程、测验、问答、报告和设置。
- Analyzer 负责静态分析源码。
- Agent 负责生成学习路线、课程、测验、评估、补课和面试材料。
- Service 负责串联业务流程，例如分析服务、课程生成服务、问答生成服务、源码浏览服务。
- Repository 负责 SQLite 持久化。

## 6. 核心流程

V1 主闭环是：

```text
上传 ZIP
  -> 安全解压
  -> 文件扫描
  -> AST 静态分析
  -> 构建依赖图和调用链
  -> 生成架构图
  -> 读取学习画像
  -> 生成学习路线
  -> 生成课程
  -> 生成测验
  -> 评估答案
  -> 更新掌握度
  -> 推荐下一节或生成补课
```

面试时可以强调：

> 我把 AI 问答变成了一个完整学习闭环，而不是停留在单次解释代码。

V2 变更理解闭环是：

```text
粘贴 git diff
  -> 提取变更文件
  -> 结合静态依赖图找受影响文件
  -> 命中相关 API 路由和学习课程
  -> 生成 Diff 影响分析
  -> 生成 PR 讲解包
  -> 生成增量学习建议
  -> 围绕文件、函数和 diff 继续源码追问
```

面试时可以这样串起来：

> V1 解决“如何看懂一个项目”，V2 解决“项目发生变更时如何判断影响范围、如何评审、如何复习和如何继续追问”。这让 RepoTutor 从代码学习工具进一步靠近项目接手助手。

## 7. 核心模块职责

### 7.1 安全上传

核心文件：`backend/app/utils/safe_zip.py`

做了这些安全限制：

- ZIP 最大 20 MB。
- 解压后最多 2000 个文件。
- 单文件最大 1 MB。
- 禁止绝对路径。
- 禁止 `../` 路径穿越。
- 跳过软链接。
- 跳过 `.env`、私钥、证书、`.git` 等敏感内容。
- 只解压到隔离目录。

面试回答模板：

> 上传项目代码是高风险入口，所以我没有直接信任 ZIP 内容。解压前检查大小和文件数量；解压时检查路径穿越、绝对路径、软链接和敏感文件；同时项目只做静态读取，不安装依赖、不导入上传项目、不运行用户代码。

### 7.2 静态分析

核心文件：

- `backend/app/services/analysis_service.py`
- `backend/app/analyzers/ast_parser.py`
- `backend/app/analyzers/dependency_analyzer.py`
- `backend/app/analyzers/importance_scorer.py`

静态分析提取：

- 文件路径、类型、行数、重要度。
- import 依赖。
- 函数、类、签名、装饰器、docstring。
- FastAPI 路由。
- SQLAlchemy 模型。
- Pydantic Schema。
- 函数级调用关系。

回答模板：

> 我没有通过导入项目来分析代码，而是用 Python AST 解析源码。这样不会执行用户代码，安全性更高。AST 解析后会提取函数、类、装饰器、调用表达式，再结合文件路径和 import 关系构建项目事实库。

### 7.3 FastAPI 路由识别

核心逻辑在 `AstParser._route_from_function`。

识别方式：

- 遍历函数装饰器。
- 判断装饰器是否是 `.get`、`.post`、`.put`、`.patch`、`.delete` 等 HTTP 方法。
- 提取第一个字符串参数作为路由路径。
- 提取 response_model 和 dependencies。
- 记录处理函数名和行号。

面试官问“怎么识别路由”时可以答：

> FastAPI 路由本质上是函数装饰器，例如 `@router.post("/login")`。我通过 AST 找到 FunctionDef，再遍历 decorator_list，如果装饰器是 Call，并且 func 是 get/post/put/delete 这类 HTTP 方法，就把它识别为路由，记录 method、path、handler、line 和 response_model。

### 7.4 SQLAlchemy 模型识别

核心逻辑在 `AstParser._model_from_class`。

识别依据：

- 类继承名类似 Base 或 SQLModel。
- 类体内包含 `Column(...)` 或 `mapped_column(...)`。
- 提取 `__tablename__`。
- 提取字段、主键、外键和 relationship。

可以这样讲：

> 对 ORM 模型没有运行项目，而是分析类定义。只要类继承类似 Base，或类体里出现 Column、mapped_column、relationship，就认为它可能是数据模型，再解析字段、主键、外键和表名。

### 7.5 Pydantic Schema 识别

核心逻辑在 `AstParser._schema_from_class`。

识别方式：

- 判断类是否继承 `BaseModel`。
- 读取类体中的 AnnAssign。
- 提取字段名、类型、是否必填、默认值。

可以这样答：

> Pydantic Schema 的核心特征是继承 BaseModel，并通过类型注解定义字段。所以我通过 AST 解析 ClassDef 的 bases 和 AnnAssign，就能拿到请求响应结构。

### 7.6 文件重要度评分

核心文件：`backend/app/analyzers/importance_scorer.py`

评分依据包括：

- 是否包含 FastAPI 入口。
- 是否包含 API 路由。
- 是否位于 services、repositories、models、core 等目录。
- 是否被其他模块 import。
- 测试和迁移文件权重较低。

面试回答：

> 学习陌生项目的第一步是知道先看哪些文件。我用可解释规则做文件重要度评分，而不是完全依赖 LLM。比如入口文件、路由文件、服务层、仓储层、模型层权重更高，被多个文件 import 的模块也更重要。

### 7.7 文件依赖图

核心文件：`backend/app/analyzers/dependency_analyzer.py`

做法：

- 根据所有 Python 文件构建模块名到文件路径的索引。
- 解析 import 语句。
- 将 import 解析为仓库内部文件之间的边。
- 生成 `DependencyEdge`。

可以这样答：

> 文件依赖图来自 import 关系，不是 LLM 猜的。这样能保证边是可追溯的。每条边记录 source、target、edge_type 和 evidence，用于后续架构图和影响范围分析。

### 7.8 函数级调用链

核心文件：

- `backend/app/analyzers/ast_parser.py`
- `backend/app/services/call_chain_service.py`

做法分两步：

1. AST 阶段记录函数内部调用表达式，例如 `service.login(...)`。
2. 分析服务根据符号表把调用表达式解析到真实函数或方法，例如 `AuthService.login`。

CallChainService 再从路由处理函数出发，按优先级追踪到 Service、Repository。

示例链路：

```text
login -> AuthService.login -> UserRepository.get_by_email
```

面试回答模板：

> 文件依赖只能说明模块 import 关系，不能说明一次请求实际经过哪些函数。所以我又做了函数级调用链分析。AST 会记录每个函数内部调用了什么，再结合类名、方法名和 self 属性绑定关系，把调用尽量解析到仓库内真实符号。最后从 FastAPI 路由处理函数出发，优先追踪 Service 和 Repository，生成可教学的调用链。

需要补充一句边界：

> 这个调用链是静态近似，不能覆盖所有动态分发、反射或依赖注入场景，所以界面和文档里会区分 AST 确认关系和保守推断。

### 7.9 架构图生成

核心目录：`backend/app/diagrams`

V1 支持：

- 系统分层架构图。
- UML 组件图。
- UML 类图。
- 数据库 ER 图。
- 核心业务时序图。
- 部署图。
- 文件依赖图。

可以这样讲：

> 架构图不是让 LLM 自由发挥，而是基于静态分析结果生成。比如 ER 图来自模型字段和外键，类图来自类和字段，时序图优先使用真实调用链。这样可以减少幻觉。

### 7.10 课程生成

核心文件：

- `backend/app/agents/curriculum_agent.py`
- `backend/app/agents/teaching_agent.py`
- `backend/app/services/lesson_generation_service.py`

课程生成分两层：

- CurriculumAgent 生成学习路线。
- TeachingAgent 生成单节课程。
- LessonGenerationService 支持可选 LLM 增强。

课程包括：

- 为什么要学。
- 学习目标。
- 核心代码位置。
- 调用链。
- 关键讲解。
- 设计原因。
- 易错点。
- 总结。
- 测验入口。

面试回答：

> 课程不是直接把代码丢给模型总结，而是先用静态分析拿到事实，再由确定性规则生成结构化课程。配置 LLM 后，会把受控代码片段和事实传给模型增强表达，但模型输出必须经过校验，失败就回退到确定性课程。

### 7.11 事实校验和防幻觉

核心文件：`backend/app/llm/validators.py`

校验内容：

- 引用必须有 file。
- 文件必须存在于分析结果中。
- 行号必须在文件行数范围内。
- 课程和问答必须包含必要字段。
- 问答必须有事实依据和源码引用。

面试回答模板：

> 项目里最重要的安全设计之一是防止 LLM 幻觉。所有课程、问答和补课材料里的源码引用都要经过 CodeReferenceValidator 校验，文件不存在或行号越界会直接失败。LLM 输出校验失败时不会展示给用户，而是回退到确定性生成。

### 7.12 项目问答

核心文件：

- `backend/app/agents/qa_agent.py`
- `backend/app/services/qa_generation_service.py`

问答输出包含：

- answer：回答。
- facts：事实依据。
- inferences：推断。
- references：真实源码引用。
- fact_checked：事实校验结果。

回答模板：

> 项目问答不是普通聊天，它必须基于当前仓库事实库回答，并明确区分事实和推断。回答必须引用真实文件和行号，引用也会经过校验。

### 7.13 测验和评分

核心文件：

- `backend/app/agents/quiz_agent.py`
- `backend/app/agents/assessment_agent.py`
- `backend/app/graphs/learning_graph.py`

题型：

- 基础理解题。
- 代码定位题。
- 调用链题。
- 修改影响题。

评分方式：

- V1 使用关键词覆盖率。
- >= 80：MASTERED，进入下一节。
- 60 到 79：PARTIAL，稍后复习。
- < 60：NEEDS_REVIEW，生成补充讲解和二次测验。

面试回答：

> V1 的评分采用关键词覆盖率，目的是保证离线可演示和可控。虽然它不如语义评分灵活，但稳定、可测试、便于闭环。后续可以把 AssessmentAgent 换成 LLM 语义评分，但仍然保留结构化输出和校验。

### 7.14 低分补课

核心文件：`backend/app/agents/remediation_agent.py`

低分后生成：

- 薄弱点。
- 补充说明。
- 复习步骤。
- 源码证据。
- 调用链。
- 二次测验。

回答模板：

> 学习系统不能只告诉用户“你错了”，还要告诉他怎么补。所以当分数低于 60 时，系统会根据缺失点和误区生成补充讲解，并绑定真实源码位置和调用链，再生成二次测验。用户通过二次测验后，课程状态会继续更新。

### 7.15 LangGraph 工作流

核心文件：

- `backend/app/graphs/learning_graph.py`
- `backend/app/services/workflow_service.py`

当前工作流：

```text
START
  -> analyze_repository
  -> generate_architecture_views
  -> load_learner_profile
  -> generate_curriculum
  -> END
```

每个节点都会记录 Agent 运行事件。

面试回答：

> 这个项目适合用 LangGraph，因为它不是一次性接口调用，而是一个状态流转过程。导入项目时会经历分析仓库、生成架构图、读取学习画像、生成学习路线等节点。LangGraph 让每个节点职责清晰，也方便记录运行轨迹和后续扩展条件分支。

如果被追问“为什么 V1 工作流不包含测验评估”：

> V1 的导入工作流负责 onboarding，即把项目准备成可学习状态。测验评估发生在用户交互阶段，是另一个运行时闭环。后续可以把测验评估和补课也纳入 LangGraph 条件边。

### 7.16 LLM 接入

核心文件：

- `backend/app/llm/client.py`
- `backend/app/services/lesson_generation_service.py`
- `backend/app/services/qa_generation_service.py`

设计原则：

- OpenAI 兼容接口。
- API Key 可通过环境变量或界面配置。
- 没配置 API Key 时使用确定性规则。
- LLM 输出必须是 JSON。
- LLM 输出必须经过事实校验。
- 记录 prompt、response、状态、错误和耗时。

回答模板：

> V1 不是强依赖 LLM，而是确定性规则优先。LLM 只是增强表达质量。这样即使没有模型接口，系统也能完整跑通 Demo；配置模型后，会记录调用审计，并对模型输出做结构和源码引用校验。

### 7.17 数据库设计

核心文件：`backend/app/repositories/sqlite_repository.py`

主要表：

- projects：项目基本信息。
- learner_profiles：学习画像。
- analysis_results：静态分析结果 JSON。
- diagrams：架构图。
- learning_plans：学习计划。
- lessons：课程。
- quizzes：测验。
- quiz_results：测验结果。
- mastery_records：掌握度。
- agent_runs / agent_run_events：Agent 运行记录。
- llm_call_logs：LLM 调用审计。

为什么用 SQLite：

> 当前版本以本地演示和单人学习为主，SQLite 部署简单、零运维、足够支撑 Demo。后续如果进入多用户协作，再迁移 PostgreSQL 或其他数据库。

### 7.18 前端设计

核心目录：`frontend/pages`

页面包括：

- Home：项目导入。
- Project Overview：项目概览。
- Architecture Diagrams：架构图。
- Learning Plan：学习路线。
- Lesson Quiz：课程与测验。
- Project QA：项目问答。

### 7.22 Diff 影响分析

核心文件：`backend/app/services/diff_impact_service.py`

输入是一段 `git diff` 文本。服务会做这些事：

- 从 `diff --git`、`---`、`+++` 中提取变更路径。
- 判断变更文件是否属于当前项目分析结果。
- 根据 import 反向依赖图找到受影响文件。
- 根据业务命名启发式补充同领域文件，例如 `orders.py`、`order_service.py`、`order_repository.py`。
- 汇总相关路由和相关课程。
- 计算风险等级：LOW、MEDIUM、HIGH。

面试回答模板：

> Diff 影响分析不是执行代码，而是把 diff 里的路径映射回静态分析事实库。它会先找变更文件，再沿着反向 import 依赖图找调用方，同时用业务命名做保守补充。最后把相关路由、课程和风险等级一起返回，帮助用户避免只看改动文件。

边界说明：

> 这仍然是静态影响分析，不能替代测试。它的价值是给出回归检查范围和阅读顺序，而不是证明代码一定没问题。

## 8. 面试高频问答

### Q1：这个项目和普通 ChatGPT 问代码有什么区别？

普通问答是一次性的，它回答一个问题就结束了。RepoTutor 是一个学习系统，它会先建立项目事实库，再生成架构图、学习路线、课程、测验、掌握度和补课材料。它关注的是持续学习闭环，而不是单次解释。

### Q2：为什么要用 AST，而不是直接把代码发给 LLM？

因为 AST 可以提供确定、可验证的代码事实。直接让 LLM 总结容易出现幻觉，尤其是文件路径、函数名、行号和调用关系。AST 不执行代码，安全性高，而且能稳定提取结构化信息。

### Q3：如何保证上传项目安全？

ZIP 解压前后都有安全检查：限制大小、文件数、单文件大小；禁止绝对路径和路径穿越；跳过软链接和敏感文件；只做静态读取，不安装依赖、不导入项目、不运行用户代码。

### Q4：项目如何识别 FastAPI 路由？

解析函数定义的装饰器，识别 `.get`、`.post`、`.put`、`.delete` 等 HTTP 方法，提取路径、处理函数、行号、response_model 和依赖项。

### Q5：如何识别项目入口？

通过文件路径和源码特征综合判断。比如 `main.py`、包含 `FastAPI()`、`include_router` 的文件会获得更高重要度，通常会出现在核心模块列表前面。

### Q6：怎么生成学习路线？

先根据静态分析得到项目类型、技术栈、核心模块、路由、模型和文件重要度，再结合用户画像，例如 Python 水平、FastAPI 水平、学习目标和每日时间，生成 5 到 10 节课程。

### Q7：课程怎么保证不是瞎编的？

课程里的核心代码位置必须引用真实文件和行号，输出后会经过 `LessonOutputValidator` 和 `CodeReferenceValidator` 校验。如果文件不存在或行号越界，就会失败。

### Q8：LLM 幻觉怎么处理？

LLM 只是可选增强，不是唯一生成来源。确定性课程先生成，LLM 只能在受控上下文里增强表达。LLM 输出必须是 JSON，并且必须经过事实校验；失败就回退确定性版本。

### Q9：调用链是怎么做的？

AST 解析每个函数内部的调用表达式，生成 `CallEdge`。分析服务再结合符号表，把调用名解析到仓库内函数或方法。最后从路由处理函数出发，优先追踪 Service 和 Repository，形成教学用调用链。

### Q10：调用链和 import 依赖图有什么区别？

import 依赖图说明文件之间的静态依赖，调用链说明一次请求在函数和方法之间的大致路径。前者是文件级，后者是函数级。两者互补。

### Q11：为什么用 LangGraph？

项目导入过程天然是多阶段状态流：分析仓库、生成架构图、加载画像、生成课程。LangGraph 可以把这些步骤变成明确节点，方便追踪状态、记录事件和扩展条件分支。

### Q12：为什么 V1 只把导入流程放进 LangGraph？

因为 V1 先保证核心 onboarding 稳定。测验和补课属于用户交互过程，已经通过 API 和 Agent 实现。后续可以进一步把测验评估、补课、下一节推荐纳入 LangGraph 条件边。

### Q13：架构图如何避免乱画？

架构图来源于静态分析结果。类图来自类和字段，ER 图来自模型字段和外键，时序图优先用真实调用链，依赖图来自 import。不是让 LLM 自由生成。

### Q14：为什么课程评分不用 LLM？

V1 需要离线可演示和可测试，所以先使用关键词覆盖率。优点是稳定、确定、容易写测试。缺点是语义理解不足，后续可以接 LLM 评分，但仍要保留结构化输出和审计。

### Q15：低分补课怎么实现？

测验低于 60 分后，系统根据缺失点、误区、课程相关文件和调用链生成补充讲解、源码复习步骤和二次测验。二次测验仍然复用现有评分和课程状态更新机制。

### Q16：为什么用 SQLite？

V1 是单人本地学习工具和演示项目，SQLite 简单、稳定、无需部署数据库服务。后续如果做多用户协作，可以迁移到 PostgreSQL。

### Q17：为什么前端用 Streamlit？

Streamlit 适合快速构建数据产品和 AI 工具 Demo。RepoTutor 的重点是分析和学习闭环，不是复杂前端交互，所以 Streamlit 能更快交付完整体验。

### Q18：项目最大的技术难点是什么？

最大的难点是把“代码事实”和“教学内容”绑定起来。不能只生成好看的课程，还要保证课程引用真实文件、真实函数和真实行号。因此我做了 AST 分析、调用链、事实校验和 LLM 回退机制。

### Q19：项目有哪些可扩展点？

- 支持 Django 或 Java/Spring。
- 支持 Git 历史和提交演进分析。
- 加入向量检索，增强大仓库自然语言问答。
- 引入 LLM 语义评分，替换或补充关键词评分。
- 引入运行时 tracing，提高调用链准确性。
- 增加团队空间、权限隔离和多用户协作。
- 做跨仓库知识图谱和项目 onboarding 模板。
- IDE 插件。

### Q20：项目的局限是什么？

- 目前主要面向中小型 FastAPI 项目。
- 调用链是静态近似，无法完全覆盖运行时动态分发。
- 评分是关键词覆盖，不是深度语义理解。
- 架构图偏事实展示，不是完整企业级建模。
- 当前默认本地单用户，没有复杂权限和团队协作。

### Q21：Diff 影响分析是怎么做的？

先从 `git diff` 文本里解析变更文件，再判断这些文件是否存在于当前静态分析结果。对于已识别文件，系统会沿着反向 import 依赖图找到调用方和受影响文件，同时根据业务命名做补充匹配，例如订单 API、订单 Service、订单 Repository。最后汇总变更文件、受影响文件、相关路由、相关课程和风险等级。

### Q22：PR 讲解包解决什么问题？

它解决的是“如何把一次改动讲清楚”。Diff 影响分析告诉你影响哪里，PR 讲解包进一步把它整理成评审清单、测试计划、学习影响、面试复盘说法和合并建议。这样用户不仅能看懂 diff，还能知道 PR 里该写什么、评审时该检查什么。

### Q23：增量学习建议和学习路线有什么区别？

学习路线是项目级的，从零开始系统学习。增量学习建议是变更级的，围绕一次 diff 推荐需要复习的课程、源码检查点和练习任务。一个偏长期路线，一个偏当前改动。

### Q24：源码追问和项目问答有什么区别？

项目问答回答的是项目级问题，例如入口、登录流程、JWT 配置。源码追问更聚焦，可以指定文件、函数、类和 diff，返回相关文件、路由、调用边、课程和源码检查点。它适合在看某个文件或某次变更时继续追问。

### Q25：源码追问是不是 RAG？

当前版本不是传统向量数据库 RAG，而是结构化事实检索。它基于 AST 分析出的文件、符号、路由、调用边、课程关联和 diff 影响范围进行匹配。优点是引用可控、事实边界清晰；缺点是语义召回不如向量检索灵活。

### Q26：项目如何做面试包装？

项目有 InterviewAgent 生成项目介绍、架构讲述、高频问答、风险提示和源码证据；还有 InterviewReadinessService 根据课程进度、练习、测验和面试题掌握状态生成面试准备度。报告导出可以把这些材料整理成 Markdown，用于背诵和复盘。

### Q27：项目仪表盘的意义是什么？

项目仪表盘把分析、学习、练习、面试、演示和工程改进六个维度汇总成一个整体状态。它的价值是让用户知道项目是不是已经达到可展示、可复习、可继续优化的状态，而不是只看到零散页面。

### Q28：如果要上线成多用户产品，最先改哪里？

第一是数据库，从 SQLite 迁移到 PostgreSQL。第二是项目隔离和权限模型，每个用户只能访问自己的仓库和报告。第三是异步任务队列，因为分析仓库和生成报告可能比较耗时。第四是对象存储，用于保存上传 ZIP、分析产物和导出文件。第五是审计和敏感信息过滤。

### Q29：如何证明这个项目不是纯 Demo？

可以从工程闭环讲：它有安全解压、静态分析、事实校验、SQLite 持久化、API、Streamlit 多页面、Docker Compose、CI、pytest、离线验证、Agent 评测、E2E 验证和 GitHub 推送记录。不是只写了一个聊天页面，而是完整地处理了上传、分析、教学、测验、补课、报告和变更理解。

### Q30：当前版本最强的亮点是什么？

最强亮点是“事实库 + 教学闭环 + 变更理解”三者结合。AST 事实库保证回答和课程有依据；教学闭环让用户能学习、测验、补课；变更理解让系统能围绕 diff 做影响分析、PR 讲解、增量学习和源码追问。

## 9. 深挖问题回答模板

### 9.1 面试官问：你这个项目怎么体现 AI？

不要只说“用了 OpenAI 接口”。更好的回答是：

> 项目里的 AI 不是简单聊天，而是被放在一个受控学习系统里。系统先用 AST 建立项目事实库，再把受控上下文给 LLM 做课程和问答增强。LLM 输出必须是结构化 JSON，并经过源码引用校验。如果校验失败就回退到确定性规则。所以 AI 在这里负责表达和教学增强，事实基础来自静态分析。

### 9.2 面试官问：如果 LLM 返回不存在的文件怎么办？

回答：

> 所有源码引用都会经过 CodeReferenceValidator。它会检查 file 是否存在于分析结果中，line 是否在文件行数范围内。如果不合法，就抛出 OutputValidationError。课程生成服务捕获错误后会记录审计日志，并回退到确定性课程。

### 9.3 面试官问：为什么不用向量数据库？

回答：

> V1 的核心目标是对中小型 FastAPI 项目建立结构化事实库。文件、函数、路由、模型、Schema、调用链这些信息用 AST 和 SQLite 已经足够表达。向量数据库更适合语义检索，后续可以在大仓库问答里加入，但 V1 先保证事实准确和闭环稳定。

### 9.4 面试官问：这个项目怎么做修改影响分析？

回答：

> 当前版本已经有专门的 DiffImpactService。它会从 git diff 里提取变更路径，把路径映射回静态分析结果，再根据反向 import 依赖图和业务命名启发式找到受影响文件。同时它会汇总相关路由和相关课程，给出风险等级。这个结果还会继续传给 PR 讲解包、增量学习建议和源码追问页面。

### 9.5 面试官问：调用链为什么不一定准确？

回答：

> 因为它来自静态分析。Python 有动态调用、依赖注入、反射、猴子补丁等特性，AST 无法 100% 还原运行时行为。所以我在设计上把调用链定位为“教学用可解释路径”，并保留 confidence 和 evidence，避免把推断说成绝对事实。

### 9.6 面试官问：为什么不直接运行用户项目来分析？

回答：

> 安全风险太高。用户上传的项目可能包含恶意代码、环境变量读取、网络请求或破坏性逻辑。所以 V1 明确不安装依赖、不导入项目、不运行测试，只读取文本源码做静态分析。

### 9.7 面试官问：项目怎么支持不同学习者？

回答：

> 上传时用户会选择 Python 水平、FastAPI 水平、学习目标和每日学习时间。CurriculumAgent 会根据这些信息和项目复杂度生成课程数量、课程顺序和学习重点。例如面试目标会更强调项目讲解和调用链，修改项目目标会更强调模型、Schema、Service 和测试影响范围。

### 9.8 面试官问：Agent 是怎么拆分的？

回答：

> 我把 Agent 按职责拆分：CurriculumAgent 生成学习路线，TeachingAgent 生成课程，QuizAgent 生成测验，AssessmentAgent 评分，RemediationAgent 低分补课，QAAgent 项目问答，InterviewAgent 面试准备。这样每个 Agent 输出结构清晰，也方便单独测试和替换。

### 9.9 面试官问：为什么做低分补课？

回答：

> 因为学习闭环不能停在评分。用户低分时，系统应该给出下一步动作。低分补课会结合缺失点、误区、源码证据和调用链，生成补充讲解和二次测验，让用户可以继续学习，而不是只看到一个分数。

### 9.10 面试官问：你如何验证这个项目真的可用？

回答：

> 我有四层验证：第一是 pytest 覆盖各模块；第二是 verify_offline 验证不依赖 Web 的核心闭环；第三是 evaluate_agents 检查 Agent 输出质量和事实引用；第四是 e2e_demo_inprocess 模拟完整 Demo 流程。CI 会在 main 分支自动跑这些命令。

## 10. 项目亮点总结

可以背这六点：

1. **安全边界清晰**：上传代码只静态读取，不执行，ZIP 解压有路径和敏感文件限制。
2. **代码事实可靠**：AST 提取路由、模型、Schema、函数和调用链。
3. **防幻觉设计**：课程、问答、补课都要经过源码引用校验。
4. **学习闭环完整**：学习路线、课程、测验、掌握度、补课、报告全链路。
5. **变更理解闭环**：Diff 影响分析、PR 讲解包、增量学习和源码追问形成 V2 能力。
6. **工程化完整**：FastAPI、Streamlit、SQLite、LangGraph、Docker、CI、测试、发布文档齐全。

## 11. 项目不足和改进方向

不足：

- 只支持 Python/FastAPI，中小型项目效果最好。
- 调用链是静态近似，无法覆盖所有运行时行为。
- 评分是关键词匹配，语义理解不足。
- Streamlit 适合 Demo，但复杂交互能力有限。
- SQLite 适合单人本地，团队协作需要更强数据库和权限模型。

改进：

- V2.x：补充 Git 历史分析，把一次提交、多个提交和 PR 演进过程纳入理解范围。
- V2.x：增强语义检索，把结构化事实库和向量检索结合起来。
- V2.x：接入 LLM 语义评分，但保留结构化输出、审计和回退。
- V3：支持 Django、Java/Spring、团队项目接手模式和 IDE 插件。
- V3：引入团队空间、权限隔离、审计和跨仓库知识图谱。

## 12. 3 分钟讲解稿

> RepoTutor 是我做的一个 AI 代码导师项目，目标是帮助用户系统学习和接手一个陌生的 Python/FastAPI 仓库。用户上传 ZIP 或导入公开 GitHub 仓库后，系统会先做安全解压，限制文件大小、路径穿越、软链接和敏感文件，并且不执行用户代码。
>
> 后端通过 Python AST 做静态分析，提取文件、函数、类、FastAPI 路由、SQLAlchemy 模型、Pydantic Schema、import 依赖和函数级调用链。基于这些项目事实，系统会生成架构图、学习路线、课程讲解、测验和掌握度反馈。
>
> 我比较重视防幻觉，所以课程和问答都必须引用真实文件和行号，并经过校验。如果 LLM 输出不存在的引用，就会回退到确定性内容。
>
> 学习闭环上，用户完成课程测验后，系统会评分并更新课程状态。如果低于 60 分，还会自动生成补充讲解、源码复习步骤和二次测验。V2 又加入了 diff 影响分析、PR 讲解包、增量学习建议和源码追问，帮助用户围绕一次代码变更做复习和评审。
>
> 技术栈上，后端是 FastAPI，前端是 Streamlit，数据库是 SQLite，工作流用 LangGraph，LLM 接口兼容 OpenAI。项目还有 Docker Compose、CI、离线验证、Agent 评测和端到端 Demo。

## 13. 5 分钟讲解稿

可以按这个顺序讲：

1. 背景：陌生项目学习困难，不知道入口、调用链、核心模块，也缺少测验反馈。
2. 目标：把代码仓库变成学习课程，而不是只做一次性问答。
3. 安全：ZIP 安全解压，不执行上传代码。
4. 分析：AST 提取路由、模型、Schema、依赖和调用链。
5. 教学：生成架构图、学习路线、课程和测验。
6. 反馈：评分、掌握度、低分补课、二次测验。
7. 防幻觉：源码引用校验，LLM 失败回退。
8. 变更理解：Diff 影响分析、PR 讲解包、增量学习、源码追问。
9. 工程：FastAPI、Streamlit、SQLite、LangGraph、Docker、CI。
10. 局限：静态分析不是运行时真相，评分还不是语义评分，团队协作还没做。
11. 迭代：Git 历史、语义检索、多框架、多用户和 IDE 插件。

## 14. 面试时最应该主动强调的点

优先强调这几句话：

- “我没有让 LLM 直接自由总结，而是先建立项目事实库。”
- “所有课程和问答都要引用真实文件和行号，并经过校验。”
- “调用链不是 import 图，而是函数级调用路径。”
- “低分后不是只给分数，而是生成补充讲解和二次测验。”
- “V2 不只看 diff 文件，还会推导受影响文件、相关路由和需要复习的课程。”
- “项目可以在没有 LLM API Key 的情况下完整离线演示。”

## 15. 容易被追问的风险点

### 风险 1：静态调用链不完整

应对：

> 是的，所以我把它定位为教学用调用链，并保留证据和置信度。对动态行为，后续可以结合运行时 tracing 或测试覆盖来增强。

### 风险 2：关键词评分不够智能

应对：

> V1 选择关键词评分是为了可控和可测，后续可以接 LLM 语义评分，但仍然要保留结构化结果、审计和回退。

### 风险 3：Streamlit 不适合复杂产品

应对：

> 当前目标是快速完成 AI 工具 Demo 和学习闭环。后续如果做正式产品，可以把前端迁到 React 或 Next.js。

### 风险 4：SQLite 不适合多人使用

应对：

> 当前版本是本地单人学习工具，SQLite 部署简单。团队协作和多用户权限属于后续版本，可以迁移 PostgreSQL。

### 风险 5：LLM 成本和稳定性

应对：

> 系统默认用确定性规则，不依赖 LLM。LLM 只是增强项，并且有失败回退和调用审计。
