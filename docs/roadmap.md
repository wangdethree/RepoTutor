# RepoTutor 路线图

本路线图用于约束后续开发，避免 V1 完成后继续无边界地横向扩展。

## 当前状态

- `V1.0.0`：主闭环完成，可演示、可验收。
- 当前重点：发布收尾、演示材料、稳定性验证。
- 下一个研发阶段：V1.1 或 V2，取决于是否优先做产品打磨还是能力扩展。

## V1.1：导入与展示增强

目标：在不改变核心学习闭环的前提下，降低使用门槛并增强可视化体验。

建议范围：

- GitHub URL 导入。
- PyVis 或类似方案的交互依赖图。
- 多目标学习画像，例如同时选择“面试准备”和“学会修改项目”。
- 课程导出 Markdown。
- Demo 数据和演示截图整理。

不建议加入：

- 新语言或新大型框架支持。
- 团队协作。
- 自动修改用户代码。

## V1.2：学习体验增强

目标：让用户从“看懂项目”推进到“能动手修改项目”。

建议范围：

- 动手任务。
- Git Diff 检查。
- 课程知识卡片。
- 更细粒度复习提醒。
- 面试模式打磨和项目讲解稿导出。

验收标准：

- 每节课程至少能生成一个可执行的学习任务。
- 用户提交修改说明或 diff 后，系统能指出影响范围和遗漏点。
- 复习提醒能基于测验历史和掌握度排序。

## V2：框架与项目接手能力扩展

目标：从 FastAPI 学习导师扩展为更通用的项目接手助手。

建议范围：

- Django 项目支持。
- Java/Spring 项目支持。
- Git 历史分析。
- 项目决策历史提取。
- 团队项目接手模式。
- 多用户协作。
- IDE 插件原型。

关键风险：

- 多语言分析会显著增加解析器复杂度。
- Git 历史和团队协作会引入权限、隐私和数据模型问题。
- IDE 插件会改变交互方式，需要重新设计最小闭环。

## V3：组织级代码学习平台

目标：从单人学习工具升级为组织级知识沉淀平台。

探索方向：

- 跨仓库知识图谱。
- 团队知识库和项目 onboarding 模板。
- 代码变更影响评审。
- 架构决策记录自动生成。
- 与 issue、PR、文档系统联动。
- 权限隔离、团队空间和审计。

进入 V3 的前置条件：

- V2 已经验证多框架和团队接手场景。
- 有稳定的用户数据和真实使用反馈。
- 数据权限、项目隔离和审计模型成熟。

## 推荐下一步

短期建议先做 V1 发布收尾：

1. 打 `v1.0.0` Git tag。
2. 录制或整理一套 Demo 演示路径。
3. 选择 V1.1 的一个小目标作为下一轮开发入口。
